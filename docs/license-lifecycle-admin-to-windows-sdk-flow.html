License lifecycle · Windows target

From admin creation to Windows SDK verify

A field-level walkthrough of what happens, who does it, and which API each step calls — from a Dcorp admin creating a license in skyapp-api to a Windows desktop app (via skylicense-core-sdk) verifying and enforcing it.

Verified against skyapp-api HEAD and skylicense-core-sdk core/src/commonMain on 2026-10-14. Every claim below cites a file:line — see Source citations.

iScope & actors

ⓘ
Two completely independent trust domains Everything under "Admin side" happens inside skyapp-api, is operated by Dcorp staff, and never touches the SDK directly. Everything under "Client side" runs inside the end user's Windows machine and only ever sees the public HTTP API — never the database, never an admin credential. The only thing that crosses the boundary is the license key (given to the user out-of-band, e.g. by email after purchase) and the signed JWT the SDK receives from /verify.

An admin typically sets Status=Active either at creation or via the general update endpoint before handing the key to a customer.

ⓘ
Anonymous endpoint LicenseSettingController is explicitly [AllowAnonymous] — the SDK calls it directly (no admin credential), using the same public surface the end user's app has access to. This is intentional: the SDK needs these values to decide offline behavior without a server round-trip to an auth system it doesn't have credentials for.

DWindows app integrates the SDK

This happens once, at Dcorp's build time — not per end user.

1
Obtain the trusted signing public key
KDcorp dev

There is no JWKS/public-key discovery endpoint on skyapp-api — the signing key is auto-bootstrapped per environment server-side. Dcorp must obtain the current public key out-of-band (ops handoff) and embed it in the app's config, keyed by kid (key version) so rotation doesn't break already-shipped builds.

TokenSigningService.cs:54-77,113,117 · docs/ops-signing-keys-and-pins-runbook.md

2
Call lc_create once, at process start
KWindows app
const char *config_json =
    "{\"baseUrl\":\"https://your-skyapp-api-host\",\"orgId\":123,"
    "\"appSalt\":\"a-stable-per-app-secret\","
    "\"trustedSigningKeys\":{\"v1\":\"-----BEGIN PUBLIC KEY-----\n...\n-----END PUBLIC KEY-----\"}}";

lc_handle h = lc_create(config_json);

orgId must match the BuyerOrganizationId's org used in Phase C's settings — a mismatch means the SDK reads the wrong org's allowOffline/interval. appSalt is a stable per-app secret that gets hashed together with the raw platform device id (HKLM\...\MachineGuid on Windows) before anything is sent to the backend — the backend never sees the raw hardware id.

4
SDK verifies the token locally before trusting anything
KSDK

Checks the ES256 signature against trustedSigningKeys[kid] from the app's own config (never fetched from the network), then checks exp, iss, and that the token's did claim matches this device's hashed id. No step before this one is trusted.

FBackground recheck & offline grace

Once lc_start is called, the SDK's scheduler ticks every checkIntervalMinutes and runs checkNow():

Introspect resultSDK action
isRevoked=trueClear cache immediately → Revoked (device was released/token revoked server-side, possibly by an admin action in Phase G)
isExpired or remaining time < one intervalCall /verify again to refresh the token (same code path as Phase E)
Still valid and freshKeep the cached token, just bump the last-checked timestamp
Network unreachableClockRollbackGuard checks for a tampered system clock, then OfflineGracePolicy decides Valid(Offline, graceUntil=token.exp) or NetworkRequired

Everything below can happen at any point after Phase B, entirely inside skyapp-api, with zero coordination from the Windows app — the SDK only finds out on its next introspect tick (Phase F) or next explicit checkNow().

!Security & authorization notes

⚠
No authentication/authorization was found on either surface in this repo A repo-wide search found app.UseAuthorization() wired (CommonStartup.cs:69) but no AddAuthentication, no JWT bearer scheme, and no [Authorize] attribute anywhere in Presentation/Web.Api — including LicenseController (the admin create/revoke/renew/transfer endpoints from Phase B and Phase G). At the ASP.NET layer, the admin endpoints and the SDK's public endpoints are equally unauthenticated. If Dcorp gates admin access, it must be enforced upstream (API gateway, internal network/VPN restriction, or a front-end login that this repo doesn't implement) — this was not located in skyapp-api itself. Confirm this is intentional before treating the admin API as safe to expose beyond a trusted network.
✓
What is enforced The SDK never trusts the network response on its own — every token is verified locally against a key baked into the app at build time (Phase D), and the device-id binding (did claim) stops a leaked token from working on a different machine. The weak point is entirely on the admin-API authorization side, not the client-side trust model.
